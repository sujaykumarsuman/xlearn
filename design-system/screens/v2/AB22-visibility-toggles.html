AB22 · Visibility toggles

A new Settings tab, Profile & visibility, decides what the public profile (AB06) shows: the whole profile Public / Private, and one toggle per enrolled course whose default comes from the course manifest (D7: visible, except behavioral). Going private or hiding a course asks first and applies immediately; a private profile is indistinguishable from an unknown username.

State

  • New rail tab Profile & visibility (?tab=visibility), between Reminders and Sign-in & security. Read from GET /api/me → visibility: {profile, courses: [{slug, visible, default}]}.
  • Profile switch Public / Private (P5) with the public URL, Copy link and View profile (opens AB06 in a new tab).
  • One row per enrolled course, with its manifest default as a hint: "Default: visible (set by the course)" / "Default: hidden (set by the course)" (D7; behavioral is the hidden one, drawn illustratively since it isn't active yet).
  • A preview course is listed but disabled (ADR-0034 §2 hides it from every public surface; a toggle would change nothing).

Writes

  • Each change → PATCH /api/me/visibility with a partial body ({"profile":"private"} or {"courses":{"dsa":false}}). The BFF bumps the cache epoch and purges the negative-404 entry before it answers, so the public page changes on the very next request.
  • Going private (F2) and hiding a course (F3) confirm first. Going public or showing a course applies directly. No optimistic write: the switch shows "Saving…" until the server answers (F5).

Decision · a11y · narrow

  • P5 · D7 · P6 · ADR-0033 §13 (toggle → synchronous epoch bump).
  • Real <button role="switch" aria-checked> elements with names that include the course; Space / Enter toggle. The state word ("Public", "Visible", "Hidden") sits beside each switch, so colour is never the only cue. Text 15:1, dim 6.8:1, teal 9.0:1.
  • < 1024 px: F6.
